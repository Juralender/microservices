# Общая инфраструктура

Traefik, Keycloak и Kafka — это компоненты сквозной инфраструктуры, от которых зависят все остальные сервисы.
Novu используется лишь одним сервисом (Notification): это готовое решение для самостоятельного развертывания (self-hosted).

## API-шлюз / BFF (Traefik)

**Назначение и область применения**: единая точка входа для всех клиентских приложений 
(мобильного приложения, веб-версии, портала владельца магазина, портала корпоративного администратора, системы отображения заказов на кухне, приложения для водителей).
[Traefik](https://traefik.io/) выполняет терминацию TLS, ограничивает частоту запросов (rate limiting) для каждого клиента и маршрутизирует 
запросы к соответствующим бэкенд-сервисам на основе правил, заданных для путей (path) или хостов (host). 
Он не содержит бизнес-логики или собственных постоянных данных — только конфигурацию маршрутизации и промежуточного ПО (middleware).

**Аутентификация**: промежуточное ПО `forward-auth` в Traefik делегирует проверку токена каждого запроса сервису **Keycloak** еще до того, 
как запрос попадет на бэкенд. Это реализуется исключительно через конфигурацию, а не через разработку или самостоятельное обслуживание сервиса аутентификации.

**Взаимодействие с нижестоящими сервисами**: стандартный синхронный обмен данными по протоколу REST/JSON поверх HTTPS;
запросы передаются напрямую к публичному API каждого сервиса (описанному в соответствующей документации) без изменений —
шлюз не трансформирует полезную нагрузку (payload).

## Провайдер идентификации (Keycloak)

**Назначение и область применения**: [Keycloak](https://www.keycloak.org/) выступает в роли централизованного провайдера идентификации
(на базе стандартов OAuth2/OIDC) для всех пользователей: клиентов, владельцев франшиз, корпоративных сотрудников, персонала магазинов и водителей службы доставки.
Он выпускает и подписывает JWT-токены, которым доверяют все остальные сервисы, а также управляет учетными записями пользователей, учетными данными 
и атрибутами ролей/арендаторов (например, информацией о том, к какой франшизе относится учетная запись владельца магазина).

**Контракт взаимодействия**:
- Middleware `forward-auth` в Traefik при каждом запросе на входном шлюзе (edge)
  обращается к эндпоинтам Keycloak для проверки токена (introspection)
  или получения информации о пользователе (userinfo).
- Каждый бэкенд-сервис дополнительно проверяет JWT **локально**, используя
  публичные ключи подписи Keycloak (получаемые через эндпоинт JWKS и кэшируемые).
  Благодаря этому сервисам не нужно выполнять сетевой запрос к Keycloak
  при каждом обращении — достаточно проверки подписи и утверждений (claims):
  издателя (issuer), аудитории (audience), ролей и `tenantId`.
- Realms (области), клиенты и роли настраиваются для каждого окружения
  (dev/staging/prod) и региона (с учетом планов по выходу на зарубежные рынки).

## Инфраструктура уведомлений (Novu)

**Назначение и область применения**: [Novu](https://novu.co/) — это
инфраструктура уведомлений с открытым исходным кодом (self-hosted),
лежащая в основе нашего сервиса уведомлений (Notification Service).

**Контракт взаимодействия**:
- [Notification Service](notification-service.md) — представляющий собой
  легковесный адаптер, а не полноценную реализацию логики, — при получении
  события `OrderStatusChanged` вызывает эндпоинт `POST /v1/events/trigger`
  в Novu, передавая идентификатор сценария и полезную нагрузку (payload).
- Novu определяет предпочтительный канал связи для подписчика, формирует соответствующий шаблон 
рабочего процесса (workflow) и обращается к провайдеру (SMS, push-уведомления или email), настроенному для данного канала и региона.
- Запрос статуса или истории доставки выполняется через собственный API активности Novu по мере необходимости (например, для инструментов службы поддержки) — мы не ведем собственный журнал уведомлений.
- Рабочие процессы, шаблоны и учетные данные провайдеров настраиваются непосредственно в Novu (например, специалисты по маркетингу могут менять текст сообщений), а не развертываются как изменения кода в сервисе уведомлений (Notification Service).

## Шина событий (Apache Kafka)

**Назначение и область применения**: Kafka служит основой для передачи всех асинхронных доменных событий между сервисами (полный список см. в таблицах *Published Events* / *Consumed Events* для каждого сервиса: `OrderPlaced`, `OrderConfirmed`, `OrderReady`, `PaymentCaptured`, `PaymentFailed`, `DriverAssigned`, `DeliveryStatusChanged`, `OrderStatusChanged` и т. д.).

**Контракт**: для каждого типа события выделяется отдельный топик; за схему события отвечает сервис-источник (допускается только добавление полей с сохранением обратной совместимости и версионированием); сервисы-потребители подписываются на конкретные топики и должны обеспечивать обработку с гарантией доставки «как минимум один раз» (at-least-once delivery) — для этого используется идемпотентная обработка с ключом, состоящим из `orderId` и типа события. Прямой доступ одного сервиса к базе данных другого запрещен: единственными разрешенными точками интеграции являются шина событий и синхронные API, определенные для каждого сервиса.
